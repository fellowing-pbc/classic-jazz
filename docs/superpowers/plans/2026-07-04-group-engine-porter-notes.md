# Porter notes from Task 1 (fixture exporter) — ACTUAL TS behavior, fixtures are authoritative

1. parent_revoked_inheritance resolves to `reader` (child wins), NOT revoked. roleOfInternal collapses a direct `revoked` to `undefined` inside parentGroup.roleOfInternal(member) BEFORE the inheritance check → parentRole undefined → not inheritable → child's reader stands. isMorePermissiveAndShouldInherit's revoked branch is effectively unreachable via `extend` mappings (a `revoked` MAPPING value is skipped even earlier by `if (role === "revoked") continue`). Read-side query on the parent returns null.
2. deep_parent_chain: member writer in grandparent, revoked in parent → child STILL resolves writer at every timestamp. Parent's direct revoke collapses to undefined, then the parent RE-INHERITS writer from grandparent (parent extends grandparent), so the child inherits transitively. Mid-chain revocation does NOT block inheritance with an alternate higher-ancestor path.
3. everyone: member-with-no-role falls back to everyone's role at that time; querying member="everyone" directly does NOT use the fallback and returns the direct value, revoked collapsing to null.
4. cross_session_ties resolves to `reader`: both same-madeAt txs valid; resolution decided by TimeBasedEntry equal-madeAt-inserts-AFTER over the stable-sorted tx order. Rust sort must treat cross-session ties as equal (stable) or the tie flips.
5. private tx on group → invalid "Can't make private transactions in groups". Private tx on an ACCOUNT authored by its own agent → VALID (isGroup() false when header.meta.type==="account"; account agent is admin on own covalue).
6. write_only_keys: writeOnlyKeys[member] = change.value is assigned on EVERY writeKeyFor_ tx BEFORE the override check, even for txs then marked invalid; a member setting their OWN write key is rejected ("Write key already exists…") when the key exists and they aren't admin/manager. Own-write-key-revelation validity depends on writeOnlyKeys[member] == keyID prefix at processing time (last write wins).
7. signerID shape: agent-owned session → composite "sealer_.../signer_..."; account session → bare "signer_z...".
8. Group validation treats member ids as opaque keys; it does NOT load member accounts (only ownedByGroup does agent resolution). Fixtures include member accounts anyway for context.
9. (Task 3 reviewer note, for STAGE 3) TS compareTransactions breaks same-session ties on txID = sourceTxID ?? currentTxID (source identity for merged txs). Rust tie-breaks on the stored current (session_id, tx_index) because PendingTxIn carries only source_made_at. Spec-conformant per the stage-2 plan, but if stage 3 needs merge-branch tie fidelity, PendingTx must also carry sourceTxId.
